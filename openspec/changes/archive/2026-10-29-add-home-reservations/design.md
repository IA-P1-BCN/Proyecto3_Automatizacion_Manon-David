# Design

## Context

Observed: `POST /api/apartados` needs `cliente`, `producto`, `precio` and `abono_inicial` (minimum 5 €, at most `precio`) and answers 422 with a readable `detail` otherwise. The app has no catalogue and no "request" state, so a reservation without a deposit cannot exist in it. The `Idempotency-Key` header exists only on payment registration (`/abonos`), not on apartado creation. Creating an apartado emits `apartado.creado`, which the router (flow 00) already turns into consent recording and the flow 01 confirmation.

Flow 03 reads a bank notice, has the model extract payer, amount and concept, validates the extraction, then matches an existing `activo` reservation and registers the deposit; unmatched or doubtful payments go to a review email to Marisa. Its items carry `result`, `reason`, `payment`, `payment_key` and `allow_payment_registration`, and later nodes read their context from the node `Keep Bank Notice Context for Reservation Identification` through `itemMatching`.

Patterns reused: Form Trigger with a Form completion page (flow 10), Data Tables and `09 Consent Check` (flows 09, 10), error output on HTTP and email nodes (06b), code generated by `workflows/code/build-*.js` from pure, unit-tested helpers. See `docs/decisions-clarify.md` for the Data Table and consent decisions.

## Goals / Non-Goals

**Goals:** a customer can ask from home; Marisa gets everything needed to act in one email; the apartado is created exactly once, when the matching payment arrives, with amounts decided by the app; flow 03 behaves exactly as before for every payment that is not about a request.

**Non-Goals:** Telegram, reminders or expiry of stale requests, a catalogue, any change to the app or to flows 00 and 01, a new AI use, and recording a form-specific consent origin.

## Decisions

1. **Three pieces, each small.** Flow `11 Home Reservations` (request form, pending row, emails), sub-workflow `11b Match Pending Request` (decide, claim, create, update the row) and a three-node hook in flow 03. The matching logic lives in 11b so the edit to flow 03 stays minimal and the logic can be unit-tested. *Alternative:* put everything in flow 03; rejected, it would grow David's flow and mix two features. *Alternative:* a second flow reading the same mailbox; rejected, two readers would risk processing a payment twice.

2. **Pending requests live in the Data Table `solicitudes_apartado`.** It is the store already used for consent and the migration, needs no credential, and Marisa can read and cancel rows. Columns: `ref`, `nombre`, `telefono`, `email`, `producto`, `talla`, `precio`, `estado`, `apartado_id`, `fecha`, `payment_key`. `ref` is `SOL-` plus a zero-padded number one above the highest in the table (not the row count, so deleted rows cannot cause a repeat); it is also what the customer writes as the payment concept. *Rejected* (consistent with earlier decisions): n8n static data (invisible, lost with n8n data), kDrive CSV (a second integration for a few rows).

3. **Fixed price list in the code, shared with the form.** One list `[{ producto, precio }]` builds the dropdown labels (`Zueco cuero negro - 64,50 €`) and the lookup; the submitted label must equal a computed label, so a model with another price is rejected and the price is never read from the form. The list is mock data to be replaced by Marisa's real catalogue. A changed price affects only new requests because the price is stored in the row. *Rejected:* price typed by the customer (untrusted amount).

4. **The apartado is created when the payment arrives, by 11b.** The app forces a deposit with the apartado, and the README says the apartado is confirmed when the initial deposit arrives. 11b creates it with the request's data and the payment's amount as `abono_inicial`, `forma_pago` `bizum` (transfers are recorded as Bizum, as flow 03 does). It does not check the amount against 5 € or the price: the app decides (rule 1) and its `detail` goes to Marisa.

5. **Matching rules, strict on purpose.** A `SOL-…` reference (loosely written, normalised to four digits) makes that request the only candidate; the payer must fit its name (full-name containment or abbreviated name, the same rules as flow 03, copied because flow 03 does not export them). Without a reference the payment is taken only when exactly one pending request fits the full payer name and **no active reservation fits it**; abbreviated payers are never accepted without a reference. A payment that fits no request returns `not_mine`. Anything ambiguous returns `review`. *Rejected:* fuzzy matching and name-only matching without the reservation guard (could create an apartado for a payment that belongs to an existing one).

6. **Idempotency with a claim and a re-read.** Before calling the app, 11b updates the row `pendiente → procesando` with the payment key, then reads it again and goes on only if the stored key is its own. A second payment, or a retry of the same execution after a claim by another, stops with a review. On a 201 the row becomes `confirmada` with `apartado_id`; on 404/409/422 it returns to `pendiente` and the app's message goes to Marisa; on anything else it stays `procesando` and the answer is `uncertain`. The app has no idempotency header here, so an automatic retry is never made. *Residual risk:* Data Tables have no transactions, so the claim is not formally atomic; the re-read with the key makes the loser stop in practice, and the verification task exercises it.

7. **Updating the row can fail after the app answered.** 11b treats a failed update as `uncertain` with a message to fix the row by hand and check the app first, instead of hiding the mismatch.

8. **Hook in flow 03, before the context NoOp.** The validated-extraction node's true output goes to an Execute Workflow node (`11b`, once per item, waiting), then a Switch on `decision`: `not_mine` → the existing `Keep Bank Notice Context…` NoOp (old path unchanged), `created` → a new NoOp (end), fallback → `Prepare a Spanish Review Notice…` (so `review`, `uncertain` and anything unexpected reach Marisa). The hook must sit **before** the NoOp because later nodes read their context from it with `itemMatching`; putting it after could break the item pairing. The non-payment branch is not touched.

9. **`not_mine` changes nothing but one field.** 11b returns the item as received plus `decision: 'not_mine'`, which is what the Switch routes on. Flow 03 reads `reason` and `result` on its own item and overwrites `decision` when it matches reservations, so nothing else may change. An earlier draft returned the item untouched; that would have sent every ordinary payment to the review path because flow 03's items have no `decision`. A unit test pins the behaviour.

10. **Registration gate passed through.** 11b reads `allow_payment_registration`; when it is not `true` it returns a Spanish "Vista previa" review and writes nothing, so flow 03's test mode stays safe.

11. **No second confirmation email.** The app emits `apartado.creado` after the creation, so flow 01 sends the confirmation and the router records consent as today. Flow 03 sends the customer nothing, as its spec requires.

12. **Consent through flow 09.** Flow 11 calls `09 Consent Check` with `registrar: true`: a missing row is recorded `activo`, a `retirado` row is never overwritten and only `permitido` allows the customer email. Flow 09 does not accept an origin, so the row's origin is `tienda`. *Alternative:* add an `origen` input to flow 09 (one line); deferred to avoid editing another flow now.

13. **Public form and Spanish text.** The request form is an n8n Form Trigger with Form completion pages for the confirmation, the validation errors and the duplicate case. The customer, shop and result texts come from a tested helper (comma decimals, `5,00 €`). They are mock wording to review with Marisa. Payment instructions come from the environment variable `TIENDA_PAGO_INSTRUCCIONES` (passed through `docker-compose.yml`, fake example in `.env.example`); if empty, the email says to ask the shop. No Bizum number or IBAN is committed.

14. **Duplicate guard.** The same normalised email, model and size still `pendiente` returns the existing reference instead of a second row; a `confirmada` or `cancelada` row never blocks a new request.

15. **Error handling.** Data Table nodes stop on error (the error workflow alerts); HTTP and email nodes in flow 11 and the apartado creation in 11b use the error output so a failure is classified rather than lost. Alerts never carry names, phones or emails (as in flow 08).

## Risks / Trade-offs

- [Editing flow 03, owned by David] → get his agreement first; the hook is three nodes and two connections, the old path is unchanged, and the nine sample notices are re-run as a regression.
- [Execute Workflow input mapping is unverified for the installed n8n version] → the first preview run must show `payment`, `payment_key` and `allow_payment_registration` in 11b's input; if empty, change the mapping or the 11b trigger.
- [Data Table update filters are unverified in a real instance] → check the node shows both conditions after import and re-add by hand if not.
- [Name rules copied from flow 03 can drift] → both are small and tested; a change to one must be copied to the other until flow 03 exports them.
- [A customer pays without the reference and with a different name] → the payment goes to Marisa as today; the reservation is created on her next action (out of scope to automate).
- [Public form can be spammed] → it only writes a row and two emails; the model whitelist and the duplicate guard limit it. A captcha is out of scope.
- [Data Table lost with n8n data] → pending rows are lost; the customer still has the reference in the email.
- [Customer data in the table] → kept until the request is settled or cancelled; recorded in the AI data inventory (no AI sees it).
- [Two flow 03 copies in `workflows/` break the AI inventory test] → keep one canonical flow 03 export; never leave two IMAP listeners active.
